# Independent quality review — 2026-10-04

Reviewed the uncommitted help-draft, composer and native update changes plus adjacent submission paths. No application source changes, deployment, real-account data, credentials or model calls. No access to the denied browser endpoint. The existing full check log reports 703 backend tests passed / 7 skipped, 184 frontend tests passed, and a successful production build. That is not browser or native visual acceptance.

Follow-up: findings 1, 3 and 4 have source fixes and permanent regressions in the [input continuity update](../releases/2026-10-04-input-continuity.md), including HTTP preflight and first-message Stop. Finding 2 remains open; the visual/device evidence required by finding 5 is still separate. The evidence below describes the reviewed state before those fixes.

## 1. P1 confirmed: Stop can finish before an already-submitted message becomes queued

Evidence: `backend/athena/engine.py:79–110`. `submit` awaits model/credit checks before its session lock. It captures a reset generation but no stop generation. `stop` cancels existing runs under that lock, then returns; the older submit can acquire the lock afterward and enqueue work.

Reproduction: real Engine + a private SQLite database; hold `cloud.require_credit` on an asyncio Event, start submission while an older task is queued, await Stop, then release the credit check. The old task is cancelled, but the pre-stop submission becomes a new queued run. The actor was intentionally disabled to avoid real model/tool execution.

Regression: stop must invalidate submissions that began before it, including queue and interrupt modes, during model selection/credit/key preflight. A fresh submission after Stop must still work. Preserve the intentional interrupt-mode replacement message.

Private reproducible fixture: `/private/tmp/athena-quality-races.py` (uses only synthetic data). Run with `PYTHONPATH="$PWD/backend" uv run --directory backend python /private/tmp/athena-quality-races.py`. Root notified to implement the fix.

## 2. P1 confirmed: a lost message response makes manual resubmission duplicate work

Evidence: `src/App.tsx:523–541`, `backend/athena/api.py:312–320`, `backend/athena/engine.py:99–104`. A normal text submission retains its draft after a network error and displays only the generic fetch error. The next Send creates a new run: requests have no durable client submission identity. The voice path distinguishes unknown delivery; normal text does not. No automatic retry currently occurs, which limits but does not remove the risk.

Reproduction: execute the actual extracted `submit` handler with a synthetic server that accepts the first request and drops its response; the draft remains. Click Send again: the server accepts a second request. Separately, real Engine submissions of that identical task produce two distinct run IDs.

Regression: a network-loss-after-commit retry must resolve to the original run without repeating execution; changed user text must be a new submission. Minimum immediate UX mitigation: mark delivery as unknown and retain text without suggesting that sending failed definitely. A durable owner/session-scoped idempotency key is needed for safe retry and refresh recovery; do not deduplicate by text content.

## 3. P2 confirmed handler/state gap: partial spoken clarification is absent from the retained form

Evidence: `src/App.tsx:97,134–139,553–568,775–777`. Multi-question spoken answers only update `voiceHelpAnswers`; the form and persisted draft read `HelpDraftStore`. Hang up after answering the first of two questions: the typed form remains blank. A page reload loses the spoken answer. Starting a second clarification replaces the single in-memory record. Typed answers are likewise ignored when deciding which question to read next during a call.

Reproduction: execute the actual `submitVoice` handler for two synthetic questions; the first recognized answer is written solely to transient voice state, no help draft or backend receipt is written. This is a handler/state reproduction, not microphone/browser acceptance.

Regression: answer question one by voice, end call, answer question two by typing; both answers must remain visible and submit once. Reload and switch away/back between those steps. Use one owner/session/request-scoped draft with modality-independent updates; preserve distinct pending/answered receipts.

## 4. P2 confirmed reset omission; browser symptom needs acceptance: same attachment cannot be reselected after limit rejection

Evidence: `src/App.tsx:669–674,693,784`. File count/size validation returns before the file input is cleared. With ten attachments, choose an eleventh file, get the count error, remove one attachment and choose the same file again. Native file inputs normally emit no new change event for an unchanged selection.

Reproduction: actual extracted upload handler rejects a synthetic eleventh file while retaining the input selection. The DOM/native-picker symptom has not been exercised because browser permission is blocked.

Regression: rejected file selection is cleared; after reducing the attachment count, choosing that same file creates exactly one upload. Also cover switching conversations while an upload completes, because the `finally` input clear is guarded by the old UI scope.

## 5. Acceptance gap: passing component tests do not establish mobile/native usability

`tests/composer-actions.test.mjs:30–40` checks element props/static markup. `tests/help-drafts.test.mjs:85–107` intentionally does not simulate React commits. Their passing results cannot prove the new mobile grid fits beside voice, interrupt, Stop and Send; nor keyboard focus, touch targets, text selection, or independent Stop while the keyboard is open.

Required acceptance: 320/390px widths, long localized labels, RTL, system text enlargement, hardware/virtual keyboard, attachment tray plus three help questions, tab navigation, pending send while switching accounts and returning, and native update checks with offline/slow network while another sheet opens. Native update parsing/transport has meaningful unit coverage; its actual menu/sheet presentation remains unverified.

These temporary scripts are reproduction aids, not substitutes for permanent regression tests or end-to-end acceptance.
