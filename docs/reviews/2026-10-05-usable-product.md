# 从能力原型到实用产品

2026-10-05。根据当前源码、发布记录和三份独立只读审阅调整优先级。
以下是产品判断与待实现路线，不是已交付清单；没有进行新的真实用户研究。

## 当前判断

Athena 的实现投入集中在操作、扩展、持久化和恢复机制，普通用户需要的
完整办事流程仍有断点。注册一个组件、模型结束生成、计划完成一次唤醒，
分别只证明其中一个步骤成功。产品需要回答：用户要求的结果是否正确、
能否继续修改、离开后是否收到、换设备是否接得上。

过去的评估偏重应用设置、界面、工具协议与合成网页。保留这些底层回归，
但下一阶段的发布依据应加入独立的日常任务。测试数量不代表任务成功率。

## 先做扎实的三类事情

| 用户交办 | 应交付的体验 | 当前主要缺口 |
| --- | --- | --- |
| 把这批收据和材料清单整理成报价表；后来修改、撤销 | 接收材料，识别缺项，核对金额与来源，生成可用文件；后续只改指定内容并保留版本 | 图片/扫描件理解没有稳定流程；表格日期、百分比、公式缓存语义不足；同路径覆盖无历史原件 |
| 查一趟合适的航班，或者比较几份供应商报价 | 明确日期、预算口径和硬约束；给带来源与核验时间的候选；用户可继续筛选 | 真实查询的约束与证据验收不足；云端登录接管缺失；持久偏好不一定能召回 |
| 价格到位告诉我，明早提醒，材料到齐后继续 | 明确何时/何条件执行、在哪里执行；用户离开后能收到；故障后仍知道欠哪一步 | 用户时区缺失；触发与交付混用；系统通知未实现；持续检查失败缺少账号级关注状态 |

这些是首轮质量验证的重点，不限定 Athena 的通用能力，也不新增三个固定
产品模式。用户仍直接说话，合适的交互和结果在需要时出现。

## 按顺序推进的能力

### 1. 可信交付与可继续修改

完善默认文件技能包，包含脚本、输入检查、格式保留、输出校验和案例。
生成物直接在对话中使用；用户能说“只改这一项”“和上一版比较”“恢复上一版”。
为已交付文件保留不可变原件和版本关系。仅展示版本标记不能承诺撤销。

表格预览应区分原始数值与显示值，正确呈现常见日期、百分比和货币；公式
必须标明是否有计算证据。文档修改验证结构、样式和未要求修改的内容。
先提供可靠的自然语言修改与下载，无需先开发完整 Office 编辑器。

验收：两次修改后重启，再恢复第一版，下载字节匹配保存原件；更改人工费
不影响其他工作表；来源金额可逐项追溯，缺项明确，不能以“打开预览”代替
“计算正确”。

### 2. 可靠交办、跟进与送达

把时间绑定到用户提供或客户端报告的 IANA 时区；用户明确指定的时区优先。
保存日历规则来表达“工作日早上八点”，不要用固定秒数代替民用时间规则。
纯提醒可由调度和通知直接完成，避免到点还依赖一次模型请求才能交付。

利用已有任务、运行和事件记录区分触发、执行、待交付、送达及已读。
连续检查失败进入现有账号级待处理入口；恢复后清楚消除故障状态。
通知投递需要持久化去重与补送。未知外部动作结果先核验，不能靠自动重放
让界面看起来恢复成功。

验收：上海用户、UTC 服务器、跨午夜和夏令时用例得到正确绝对时间；页面
关闭和模型暂时不可用时，纯提醒仍有独立交付结果；复杂条件保留两次证据，
失败不会消失，网络恢复不重复提醒。锁屏/退出后的实际通知必须单独实测。

### 3. 能接手的真实浏览器任务

先验收 Mac 的登录—接管—归还—继续操作全过程，再提供云端受控接管画面。
用户在真实网页输入凭据，Athena 重新观察后继续原任务。登录失效、弹窗或
不支持的步骤要给出可完成的交接方式。

验收结果为实际下载的行程单、核对过的候选或已保存的表单；仅点击成功不算。
断线后不重复提交。查询流程保留来源、观察时间、限制和不满足项；不把搜索
摘要当作已核验的实时票价。

### 4. 随手提供资料、换设备接续

把照片、截图、扫描 PDF、录音、链接及系统分享作为真实输入场景验收。
当前有附件传输和语音接口，不代表这些材料已得到可靠理解，也不代表实际
通话的延迟、打断、嘈杂环境和来电恢复已经验收。

跨端先统一同一事项的状态、结果和待回答问题，再扩展远程执行。
本地文件按任务所需显式共享，不默认上传整台电脑。用户看到“你的电脑”
或“云端”；电脑离线时明确等待状态，不能装作手机已能访问该文件。

验收：电脑开始整理，手机追加一张收据，两端最终看到同一版本；手机能回答
缺项问题和停止同一任务；电脑休眠后恢复不重做已完成步骤。实测十分钟语音
交办、停顿、插话、录音权限拒绝，逐项记录实际失败和延迟。

### 5. 少重复解释，成功做法可以复用

自动记忆候选需要考虑当前任务、作用域和重要持久偏好，保留近期信息作为
其中一部分。纠正、撤回及当前指令优先于过时信息；无法确认的冲突不能假装
已解决。首版可采用有界词匹配和规则，不必先引入向量库或第二个模型。

“以后都按这个格式做”应将已验证流程保存成现有技能/扩展包，带输入输出、
规则、模板、验证样例和版本。下次复用既有实现，新增变化才需要生成代码。

验收：旧机场与新预算在 50 条无关记录后仍被正确使用；更新偏好后不继续用
旧值；新一批报价单能复用上次样式和校验规则，用户可以调整和撤回。

## 先修会破坏上述流程的基础缺陷

1. 落实已写好的 [durable submission receipts](../submission-intents.md)：
   网络丢回执后，用户重试同一次发送应找到原运行，不能再执行一遍。
2. 用户时区与明确日期回执；检查失败和交付失败在现有待处理入口可见。
3. 文件可恢复版本和表格显示语义；记忆召回不再限于最近 30 条。

这些修复可以与外部能力验收并行。它们不增加普通用户需要理解的工具或模式。
路线图本身不代表功能已交付。后续同日实现已补上持久发送/停止回执和任务相关词法记忆召回；详见 [发送回执](../submission-intents.md) 与 [召回验收](2026-10-05-memory-recall.md)。其余项目仍待实现或独立任务验收，发布状态另行记录。

### 首次真实报价文件验收的新增发现

后续 [表格预览修复](2026-10-05-spreadsheet-preview.md) 已保留常见金额、
百分比、日期及公式缓存状态。正式服务的一次合成报价任务完成了四项金额
核对、原样复制、下载字节校验和对话内预览。以下两项仍未通过，不能因文件
生成成功而将整个任务记为无缺陷：

- 模型叙述把“未保存计算结果”称作“结果为空”，还将保存的空字符串公式结果
  和被格式隐藏的零值混称为“不是计算结果”。界面和解析器已经区分这些状态，
  但任务推理尚未可靠使用同一语义。需要在文件操作能力/技能中提供一致的读取
  依据，并做模型端的反例验收；仅修改显示文字不能算修复推理。
- 同一结论出现在回复表格、自定义卡片和原生文件预览中。没有新增交互价值，
  增加了等待、阅读长度和工具调用。默认复用文件结果面；只有确有新的交互或
  用户要求时才创建额外组件。验收应检查没有多余注册操作、结果可直接使用，
  不以“成功创建组件”代替任务质量。

此次耗时 30.076 秒、11 次模型请求、12 次工具调用，其中两次界面操作返回
错误。按账户配置费率扣款 $0.008376，11 笔请求与扣款逐笔匹配；这不是
供应商账单。累计输入 token 缓存命中率 87.69%，但高命中率不能替代减少
无用轮次。下一轮以这些实际失败作为需求样例，比较完成耗时、请求与费用。
此次不是真实客户报价审核，也没有验证完整 Excel 重算或业务数据正确性。

后续 [统一文件读取](2026-10-05-file-runtime.md) 已把同源预览接到万能工具，
并返回绝对单元格地址和既有文件交付说明。真实模型样例已能区分三种空白
状态、引用 B7 日期并原样交付，无需再造卡片；多轮中仍出现过命令错误，
最后一次成功不能替代对间歇失败的诊断。尚未实施不可变文件历史。

[自由界面输入连续性](2026-10-05-surface-input.md) 与 iPhone 附件跳转也补了
真实使用断点：弹窗结束后继续原输入，点开附件不再替换唯一聊天页。
这有助于自由前端可用，但不等同于物理 iPhone、语音或跨执行节点接续验收。

## 证据与边界

- 自动候选与二次截断见 `backend/athena/engine.py::prepare_memory` 和
  `backend/athena/memory.py::current_memories/snapshot_note`。隔离数据库复现了
  旧机场偏好被 31 条无关记录挤出自动召回，手动查询仍然存在。
- `Engine.tick` 在排入运行时结束一次性任务。真实 Engine 配模拟模型故障
  复现了 task done / run failed；Activity 会展示失败运行，缺少的是承诺仍
  待交付的关系，不能表述为故障完全不可见。
- XLSX 预览读取单元格值，未解释样式格式；文件历史限制见
  [file revisions](2026-10-04-file-revisions.md)。
- 云端接管边界见 `backend/athena/capabilities.py`、`browser.py` 和
  [browser execution](../browser-execution.md)。
- 跨端目前共享身份与额度，任务和文件仍分执行节点，见
  [cloud deployment](../cloud-deployment.md)。
- 当前真实模型评估重点见 `scripts/evaluate_requirements.py`；独立日常任务
  集还没有足够成功率数据，不宣称“90% 已完成”。

## 下一阶段的发布判断

建立至少 20 个独立日常案例，包含缺材料、日期歧义、断网、换设备、重复
提交、文件修改和撤销。记录最终结果是否正确、用户需要接管几次、是否能
恢复、总时延和整件事成本；不能用工具调用成功或模型自报完成评分。
再让不熟悉 Agent 的用户在不接受教学的情况下试用，修正上述优先级。

我们希望形成的差异化是逐渐减少用户解释、核对与返工的负担。可变前端、
技能和 harness 为这一目标服务。它们在可靠重复使用产生数据之前，仍是
有待验证的产品假设，不能宣称已经建立护城河。
