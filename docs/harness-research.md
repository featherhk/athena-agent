# What Athena should learn from other harnesses

Reviewed 2026-10-03. Sources below are official documentation, author repositories, or product engineering articles. This is a source review, not a hands-on comparative benchmark. Documented mechanisms, published experiments, and our proposed design choices are different kinds of evidence. Names are resolved as follows: **dots = OpenAI**, **mu = qybaihe/mu**, **ZCode = Z.ai**. OpenCode findings below refer to V2.

## Product judgment

Athena's opportunity is to make durable, programmable assistance feel ordinary: tell it what you want, see whether it is doing it, interrupt it naturally, and keep the useful result. Self-modification earns its place only when it improves that experience. A registry or an attractive avatar does not establish a competitive advantage by itself.

The defensible product hypothesis is a combination: low setup burden, cross-session continuity, affordable background work, and changes that visibly work and can be undone. This remains a hypothesis until representative nontechnical users complete real tasks with little assistance. Measure successful outcomes, corrections needed, elapsed time, cost per success, and recovery after failure. Do not substitute tool-call counts or code generated for task success.

From a model's operational perspective, the useful environment provides accurate knowledge of available capabilities, inspectable current state, durable evidence of completed actions, recoverable context, and clear boundaries for changing itself. It should make it easy to discover what exists, test a replacement, and recover when that replacement fails. None of this requires pretending the model has personal needs or making self-modification the user's job.

## Source review and decisions

| Project | Mechanism supported by its sources | Application to Athena |
| --- | --- | --- |
| **Codex** | App Server separates thread start/resume/fork from turn start/steer/interrupt; steering identifies the expected turn. It exposes protocol schema generation and persistent dynamic tools. [App Server](https://learn.chatgpt.com/docs/app-server) | Use one versioned conversation protocol for web, future native clients, and acceptance drivers. Add stale-turn interruption/steering tests. Public integration APIs do not prove arbitrary replacement of Codex internals. |
| **OpenCode V2** | Plugin registrations have disposal semantics. A model request captures tool definitions and implementations, so later registrations affect later requests. Compaction has a persistent control lifecycle and retains source history. [Plugins](https://opencode.ai/v2/docs/build/plugins/) · [Compaction](https://opencode.ai/v2/docs/compaction/) | Bind requests to immutable implementation versions; apply control changes at safe boundaries. Athena already freezes custom tool bindings, but has not generalized this to all services. Keep clip-first compaction; adopting their lifecycle does not require adopting model summaries. |
| **Claude Code** | Directory plugins combine skills, agents, hooks and other integrations. Hooks distinguish lifecycle events. Programmatic operation documents interruption/recovery and isolated execution options. [Plugins](https://code.claude.com/docs/en/plugins) · [Hooks](https://code.claude.com/docs/en/hooks) · [Programmatic use](https://code.claude.com/docs/en/headless) | Package operating knowledge and resources together. Keep test accounts, plugins, and state separate from customer data. Test stop, process exit, resume, and retry separately. Lifecycle hooks alone are not a universal service replacement mechanism. |
| **DeepSeek Harness** | Contracts, providers and consumers are separate roles, with actual registered factories used to create/restore agents. Tool documentation can be generated from a running plugin composition. [Design practice](https://deepseek-harness.github.io/deepseek-harness/en/develop/practice/) · [Core](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/core) · [Tool catalog](https://deepseek-harness.github.io/deepseek-harness/en/reference/tool-catalog) | This is the closest architectural reference for a genuinely replaceable harness. A service must have a real consumer, lifecycle, state contract and replacement test. Retain Python/SQLite; split packages only where independent evolution helps. |
| **pi** | Its SDK admits runtime, session manager, resource loader and tool implementations. The session tree remains the authority for context. Its settled event distinguishes completed automatic work from an agent loop ending while follow-up work remains. Extensions require resource cleanup and run with process privileges. [SDK](https://pi.dev/docs/latest/sdk) · [Extensions](https://pi.dev/docs/latest/extensions) | Generate context from one durable history/projection path. Distinguish an individual response ending from a task settling. Do not run user-authored extension code in the secret-bearing backend process merely because a reference implementation does. |
| **mu** | Small judges operate at bounded decisions, with disabled, observation and enforcing modes and recorded decisions/latency. The author's log-admission experiment first collapses deterministic repetition while retaining recoverable originals; its judge experiment explicitly does not establish end-to-end task success. [Repository](https://github.com/qybaihe/mu) · [Experiment and limitations](https://github.com/qybaihe/mu/blob/main/kyrn/docs/09-test-log-admission.md) | Start with reversible duplicate-output folding. Evaluate a cheap judge in observation mode against no-judge and deterministic baselines before it controls evidence admission or notifications. Judge confidence is not proof of authorization or task correctness. |
| **ZCode** | Goal state persists beyond individual turns. Scheduling documents application/sleep limitations. Forks use completed-response boundaries and do not duplicate running/background work. [Goals](https://zcode.z.ai/en/docs/goal) · [Automations](https://zcode.z.ai/en/docs/automations) · [Agents](https://zcode.z.ai/en/docs/agents) | Separate a user's objective from one attempt and from its timer. Preserve partial progress without claiming a local computer works while off. Our paused job inheritance is a different explicit policy, not an exact copy of ZCode. |
| **OpenClaw** | Current automations provide durable heartbeat scheduling and quiet outcomes. Skills distinguish discovery, readiness and visibility. Memory records preserve provenance and replacement relationships. [Heartbeat](https://docs.openclaw.ai/gateway/heartbeat) · [Skills](https://docs.openclaw.ai/tools/skills) · [Memory](https://docs.openclaw.ai/concepts/memory) | Distinguish installed from usable capabilities, store wake sources, and avoid noisy unchanged updates. Its [2026.8.1 migration](https://docs.openclaw.ai/releases/2026.8.1/automations-and-scheduling) means old advice about reading HEARTBEAT.md as the runtime heartbeat should not be treated as current architecture. |
| **Manus** | Its public context-engineering article describes stable prefixes, recoverable external context and retained failure evidence. Task lifecycle distinguishes the main agent stopping from background work finishing. [Context engineering](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) · [Task lifecycle](https://open.manus.ai/docs/v2/task-lifecycle) | Persist original evidence, including snapshots when a remote source can change. Treat response completion, run completion, background settlement and acceptance as separate observations. A 2025 engineering article is evidence of published experience, not a complete description of today's closed implementation. |
| **Hermes** | Cron records dispatch attempts and unknown outcomes; it does not promise exactly-once external effects. Cheap prechecks can avoid unnecessary model wakes. Session memory snapshots preserve prefixes while new notes persist. [Cron](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron/) · [Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/) | Continue the execution ledger and no-blind-replay approach. Add attempt identity and result verification before more external actions. Local macOS supervision still needs its own implementation. No per-action approval workflow is added to Athena by this comparison. |
| **OpenAI dots** | The official product description combines persistent execution, a computer/browser, cross-channel context, inspectable activity and device connections. These are documented product capabilities, not an exposed internal harness implementation. [Introducing dots](https://openai.com/index/introducing-dots/) | Aim for continuity across devices and tasks; make progress and results available wherever the user returns. Do not infer unrestricted internal replaceability or borrow subscription economics as an API cost estimate. |
| **Muse** | Its design article describes a main ongoing chat, side chats, interrupts, background work, selective notifications, visible activity, and interactive artifacts. [Designing Muse](https://introducing.muse.ai/) | Keep familiar chat behavior, with task-specific surfaces when they help. The avatar must communicate state and offer access to activity; it should not be the only way to know what is happening. Do not add proactive suggestions before they can be useful and quiet. |
| **Grok Bot** | Persistent computers, natural messages during work, asynchronous delegation and visible files/activity are documented. Instructions from a person can redirect background work; stopping does not reverse completed actions. [Overview](https://docs.x.ai/grok-bot/overview) · [Conversation and collaboration](https://docs.x.ai/grok-bot/chat-and-collaboration) | Preserve ownership of each task and show handoffs. Nontechnical users should not need to coordinate a team of agents for ordinary tasks. Grok Build's [background memory capture](https://x.ai/news/grok-build-memory) is a related, distinct product mechanism, not evidence about Bot's internal storage. |

## Implementation order

1. **Reliable basic actions.** Send, stop, switch conversation, reconnect, authenticate, attach a file and recover a result. Each needs an observable effect and a known failure result. Test control requests against a turn ID so a delayed action cannot affect a newer turn.
2. **One context projection.** Original messages remain facts. Fork boundaries, tool clips, run exclusions and model epochs determine what is presented to the next model request. Inspection and execution must use the same projection. Prefix changes happen at persisted boundaries; a source file path or original message ID keeps clipping reversible.
3. **A real service host.** Move one entire input-to-result path behind contracts. Bind the loop, model adapter, tool executor, context builder and event writer to a composition revision. Prove replacement of a non-policy service, in-flight version stability, clean disposal, failed-candidate rollback and recovery with the normal provider unavailable. Then migrate scheduling, persistence and the remaining surfaces. This must not stop at accepting arbitrary service names.
4. **Durable goals and background execution.** Model objective, schedule, occurrence and attempt separately where their lifecycles differ. Deduplicate occurrences transactionally, coalesce stale wakes, preserve unknown outcomes, and keep conditions cheap. A goal finishes when its acceptance evidence holds. Existing timers are useful but not yet this complete goal system.
5. **Extension changes with evidence.** A registration should say what became active, where, which version, when it takes effect, how it was checked and how to restore it. Generate skill/reference contracts and validation from shared schemas where possible. Avoid a second manually maintained tool catalog.
6. **Measured improvements.** Compare duplicate folding and optional small judges on the same task corpus. Track missing necessary evidence, successful completion, correction rate, latency and total cost. Keep judge features independently switchable and begin with observation. Add demonstration-to-skill workflows later; [Codex Record & Replay](https://learn.chatgpt.com/docs/extend/record-and-replay) is a relevant user-facing pattern, distinct from deterministic engine replay tests.

## Acceptance additions

The [command-derived suite](command-acceptance.md) remains a minimum, not a declaration that all commands work. Add these adversarial variants:

- “Stop that” arrives after the visible turn finished: do not stop a newer unrelated turn.
- “Make it Chinese” means application language in one case and reply language in another; ambiguous cases must be resolved with context or a brief question.
- Update a tool after a model has received its schema: the pending call uses its bound implementation. Disable it: return an explicit unavailable outcome.
- Exclude a historical attempt, fork, restore only the parent, restart: the child's effective history must stay unchanged.
- Read a clipped result from another owned conversation: recover its original by source IDs, never replay its historical instructions.
- A condition remains true across repeated checks or the process dies after an external effect: do not silently perform that effect again.
- A plugin loads but its dependencies or consumer are absent: discovery must say unavailable/pending, not active.
- Replace the context builder with one that fails, then use fixed reset: recover default operation and retain files/history.
- Complete a task with background work still running: report those states separately instead of inventing finality.
- A novice requests a result, then changes their mind mid-task: preserve useful completed work and produce the revised result without requiring harness terminology.

Current deterministic and real-provider tests cover only a subset. Browser control, comprehensive service replacement, goal lifecycles and broad real-world task success remain work to do. The comparison supplies design decisions and test cases; it does not establish that Athena outperforms these products.
